# Agent设计‑TravelKit‑Skill运行时设计‑实现‑坑点及解决‑反思

> 
> 文档目的：沉淀TravelKit Harness Skill运行时完整架构、实现边界、踩坑总结；区分**框架层（冻结，尽量不改动）**与**业务层（订票领域，持续迭代）**；规避自研DSL、if‑else膨胀、隐式逻辑等工程陷阱。
> 背景：参考Codex‑CLI Harness拦截器模型；MCP为底层Skill协议；目标业务：航旅订票Agent。

## 1 总体概述

### 1.1 定位

TravelKit‑Harness 是Agent外部执行外壳，**不做自然语言意图解析，不实现订票业务逻辑**。
职责：

1. 管理Agent Turn循环、全局限流与死循环防护（Counter）
2. LLM输出解析 → Skill调用拦截、参数校验、参数适配、拒绝/改写
3. Skill(MCP)调用调度
4. 会话状态持久化，世界状态由外部存储维护，不完全依赖LLM上下文
5. Hook/插件调度，业务规则全部下沉业务插件

> 
> 核心思想：LLM输出Skill Call只是**申请**；Harness拥有放行、修改参数、拒绝调用的决定权。

### 1.2 边界强约束

| 层级 | 归属 | 约束 |
| --- | --- | --- |
| 框架层(Harness内核) | 框架冻结层 | 禁止出现任何业务关键字：IATA、flight、airport等；只解决“怎么跑” |
| 业务插件集合 | 业务迭代层 | 实现校验、转换业务规则；按业务能力划分，不是按Tool做wrapper |
| MCP Skill实现 | 业务迭代层 | search_flight / book_ticket 等实际能力实现 |
| Skill契约 travel‑skill‑contract‑v2.json | 配置层 | 描述Tool schema、插件引用、参数适配规则；只引用ID，不写业务逻辑与表达式 |

> 
> 架构红线：禁止在框架层写`if tool_name == "xxx"`业务分支；禁止在JSON契约内嵌入自定义DSL表达式，规避maxlang/yacc/闭包/调试困难历史坑。

## 2 核心数据结构

### 2.1 SkillCallRequest（只读DTO，来自LLM解析层）

LLM客户端解析OpenAI/Anthropic格式tool‑call后输出的纯数据对象，**只读，不允许修改**。

```
/// 来自LLM解析后的原始请求，外部输入DTO
struct SkillCallRequest {
    pub tool_name: String,
    pub raw_arguments: serde_json::Value,
    pub call_id: String,
}
```

### 2.2 SkillCallContext（框架层，拦截器核心可变上下文）

> 
> `SkillCallContext::from_request(req)`：不是NLP意图解析；仅复制DTO数据，包装可变状态壳。
> 保存原始LLM参数快照用于Debug；提供拒绝标记、警告、参数原地修改能力。

```
struct SkillCallContext {
    pub call_id: String,
    pub tool_name: String,

    /// LLM输出原始参数快照，永远只读保留，用于比对调试
    pub raw_llm_params: serde_json::Value,
    /// 工作副本，hook/插件可原地修改；最终送给MCP调用
    pub params: serde_json::Value,

    // 拦截控制状态
    pub rejected: bool,
    pub reject_msg: Option<String>,
    pub warnings: Vec<String>,

    /// 当前tool在契约中的元信息
    pub contract_tool_meta: Option<ToolMeta>,

    /// 参数适配变更日志，用于问题回溯
    pub param_adjust_logs: Vec<ParamAdjustEntry>,
}

impl SkillCallContext {
    pub fn from_request(req: SkillCallRequest) -> Self {
        Self {
            call_id: req.call_id,
            tool_name: req.tool_name,
            raw_llm_params: req.raw_arguments.clone(),
            params: req.raw_arguments,
            rejected: false,
            reject_msg: None,
            warnings: Vec::new(),
            contract_tool_meta: None,
            param_adjust_logs: Vec::new(),
        }
    }
    pub fn mark_reject(&mut self, msg: impl Into<String>);
    pub fn is_rejected(&self) -> bool;
}

#[derive(Debug, Clone)]
pub enum AdjustKind {
    RenameField,
    DropExtra,
    CoerceType,
    SetDefault,
}
#[derive(Debug, Clone)]
pub struct ParamAdjustEntry {
    pub kind: AdjustKind,
    pub before_key: Option<String>,
    pub after_key: Option<String>,
    pub old_value: Option<serde_json::Value>,
    pub new_value: Option<serde_json::Value>,
}
```

## 3 Skill完整运行时序

```
用户输入Query
    ↓
TravelKitHarness.run()
    初始化会话、加载契约、重置counter
loop {
    1. 全局counter预算检查，超限直接返回BudgetExhausted
    2. session_store.build_llm_context() 组装上下文+Skill契约
    3. llm_client.generate_skill_call()
        → LLM文本输出解析 → SkillCallRequest（只读DTO）
        解析失败直接返回RuntimeError

    4. SkillCallContext::from_request(req)
        raw_llm_params保存原始快照；params为可修改工作副本

    5. 【第一层】全局glob横切Hook执行（审计、埋点、统计）
        根据tool_name glob匹配，执行命中的横切回调

    6. 【第二层】执行业务插件 pre_plugin_ids
        读取contract中本tool的pre_plugin_ids，从插件注册表依次执行run_pre
        任意插件mark_reject → 终止后续插件；写入拒绝日志，进入下一轮turn

    7. 【框架内置适配插件 mcp_param_adapter】
        读取contract中param_adapt_rules，对ctx.params做受控变换
        所有变更写入 ctx.param_adjust_logs；不做自动猜测映射，规则必须显式配置

    8. 标准JSON‑Schema校验MCP输入schema
        校验失败 mark_reject，不调用MCP

    9. 执行MCP Skill调用，拿到skill_result

    10. 构造SkillResultContext，执行post_plugin_ids业务插件

    11. 会话持久化：持久 raw_llm_params、最终调用参数、param_adjust_logs、返回结果

    12. Harness客观判定 check_task_complete()
        true → 返回TaskComplete
    回到loop下一轮turn
}
```

> 
> 关键顺序：业务校验插件 → 参数适配插件 → JSON‑Schema校验 → MCP调用。

## 5 架构模式选择说明（历史方案对比）

> 
> 拒绝伪创新，复用工业界几十年验证的插件注册表模式；不自研迷你DSL。

| 方案 | 特点 | 取舍 |
| --- | --- | --- |
| 老式全局Hook + 内部if‑else分支 | 全部tool跑全部hook，内部if判断tool_name | ❌反模式，tool膨胀时代码爆炸，新增skill要改框架代码 |
| 契约内嵌DSL表达式 | JSON写断言表达式，追求零配置热更新 | ❌复刻maxlang全套坑：解析、闭包、报错晦涩、调试困难、性能隐患 |
| glob模式Hook Registry | 按tool名称glob匹配执行hook | ✅适合横切关注点（日志、metrics）；**禁止用于业务校验**；隐式依赖，调试困难 |
| ✅【最终选定】Hook时机 + 插件注册表 + JSON‑Schema | 契约显式声明plugin_ids；插件按业务能力划分；schema做基础类型校验 | ✅无DSL，原生代码可断点调试；新增业务语义需要写插件代码；无黑盒魔法 |

> 
> 架构要点：两层Hook体系分离
> 
> 
> 1. glob模式Hook Registry：只负责横切逻辑（日志、埋点）
> 2. Contract显式plugin_ids：负责业务校验与转换；每个tool显式声明依赖的业务插件ID。

## 6 典型坑点、现象、根因、解决方案

### 坑点1：Hook内部大量if‑else(tool_name)分支

- 现象：pre‑hook函数持续膨胀；新增skill需要修改hook调度代码；容易引入回归bug
- 根因：把业务分支写进全局hook调度层
- 解决：采用插件注册表；契约声明plugin_ids；框架调度壳写完不再改动。

### 坑点2：为追求“配置驱动”在JSON契约中嵌入表达式DSL

- 现象：看起来demo优雅；上线后遇到解析、变量闭包、报错晦涩、无法断点、性能问题，复刻maxlang历史教训
- 根因：为避免写代码，变相发明一门新语言
- 解决：简单类型交给标准JSON‑Schema；复杂业务逻辑实现为插件；契约仅引用插件ID。

### 坑点3：LLM输出tool‑call参数与MCP入参不一致；竞品可以容错，本系统严格报错被吐槽

- 现象：字段名错误、多余字段、类型错位；用户反馈“别人Agent能跑，为什么我们不行”
- 根因：两种极端：完全严格拒绝 or 无限制黑盒自动修复。
- 解决：增加框架内置`mcp_param_adapter`适配插件；配置驱动显式适配规则；保留原始参数快照与完整变更日志；提供Strict/Tolerant两级开关；适配后仍然执行schema校验。

### 坑点4：Hook只是事件通知，无法拦截与改写参数

- 现象：Hook只能做日志打印；修改参数不生效；中断流程只能抛异常，业务错误混RuntimeError
- 根因：混淆「事件通知回调」与「拦截器模式」（LangGraph/Mastra默认模式）
- 解决：采用Codex‑CLI风格拦截器模型；传入可变SkillCallContext；通过`mark_reject()`标记拒绝，业务校验失败属于业务流程，不是运行异常。

### 坑点5：业务校验逻辑写进System‑Prompt，指望LLM自觉遵守规则

- 现象：偶尔遵守，偶现违规调用；问题不可复现，调试困难。
- 根因：Prompt是软提示，不是护栏。
- 解决：System‑Prompt仅做提示；**Harness插件才是最终权威校验护栏**。

### 坑点6：依靠模型自我输出“任务完成”作为终止条件

- 现象：模型幻觉输出完成，但实际业务约束没有满足。
- 根因：把终止判断交给不可靠大模型。
- 解决：Harness框架层`check_task_complete()`客观判定是否完成，不采信LLM自我描述。

### 坑点7：隐式glob模式匹配业务校验，依赖tool名称模式

- 现象：tool改名后校验静默失效；很难静态分析一个tool实际执行哪些校验。
- 解决：glob模式只用于横切；业务校验全部走契约显式plugin_ids。

## 7 反思与设计哲学

1. **Agent Harness本质就是普通后端调度程序，不要迷信AI专属新奇架构**。插件注册表、拦截器、组件化都是成熟传统软件工程范式；价值不在于发明新算法，而在于约束团队不要滑向坏代码结构。
2. Demo追求“一份JSON搞定一切”；生产工程优先**可调试、可观测、可复现**，宁可适度写代码，不要为了零配置去造DSL。
3. LLM输出永远作为外部不可信输入；Skill调用是申请，Harness拥有否决权。
4. 区分两类能力：
   - 横切关注点（日志、埋点）：可以用glob模式隐式匹配。
   - 业务公理校验：必须显式声明依赖，拒绝隐式匹配带来的黑盒。
5. 参数兼容不等于无限制自动猜测：兼容必须可审计，每一处修改留存日志快照，便于定位“模型输出问题 / 适配层问题 / MCP服务问题”。
6. 框架层要做到：阅读框架源码搜索不到任何业务领域关键字，以此作为架构是否越界的检验标准。

## 8 后续演进约束

1. 新增Skill：优先复用已有业务插件，仅修改contract；只有出现全新业务语义才新增业务插件实现。
2. 框架层结构体、Trait、调度逻辑一旦稳定，尽量冻结；迭代全部落在业务插件、MCP Skill、contract配置。
3. 禁止新增自定义表达式语法；如果未来需要规则，优先评估是否可以封装为业务插件。



# Appendix I: 什么事skill call context

> 
> 核心疑问：
> 
> 
> 1. `llm_client.generate_skill_call(prompt_ctx).await`：LLM输出是**文本/结构化tool‑call JSON**，不是强类型对象。
> 2. `SkillCallContext::from_request(skill_call_request)` 做什么？如何把模型输出的工具调用原始数据，转成Harness可以拦截、修改、拒绝的可操作上下文对象。
> 3. 业界主流Agent（Mastra、Claude‑Code、Codex‑CLI、MCP）是不是这套流程。

先澄清现实：
大模型输出本质：**字符串**，要么是带tool_call的JSON块，要么是流式JSON片段。
模型输出 ≠ 程序内部强类型对象。
`skill_call_request` 是**解析之后的中间DTO，不是原始文本**。

---

## 完整数据流（从LLM输出文本 → SkillCallContext）

```
LLM原始输出（字节流/字符串）
        ↓
llm_client.generate_skill_call()
    1. 接收模型response，剥离system prompt、普通文本回答
    2. 解析协议（OpenAI / Anthropic / MCP tool‑call格式），提取tool name、arguments json对象
    3. 做基础反序列化，得到 SkillCallRequest（简单DTO，纯数据，无行为）
        ↓
SkillCallContext::from_request(skill_call_request)
    把只读DTO，包装成**可被Hook修改、标记拒绝、携带附加元信息的可变上下文 SkillCallContext**
        ↓
交给 pre‑hook / 业务插件：可以改params、mark_reject、注入警告
        ↓
校验通过后，才拿去执行MCP skill
```

### 两个关键结构体区分（很多Agent框架混淆二者，这就是迷惑来源）

1. **SkillCallRequest【只读DTO，来自LLM解析结果】**> 
> 纯粹映射大模型tool‑call协议，只有数据，**不能修改，没有拒绝标记**。
> 对应OpenAI `{"name":"search_flight","arguments":{"depart_code":"XXX"}}`

```
/// 来自LLM解析后的原始请求，只读，外部模型来源
struct SkillCallRequest {
    pub tool_name: String,
    pub raw_arguments: serde_json::Value, // 模型输出原始json参数，未校验
    pub call_id: String, // tool call id，模型返回
}
```

2. **SkillCallContext【Harness内部可变上下文，Hook操作对象】**> 
> `from_request()` 就是把上面只读DTO，包装成可变容器；增加hook需要的状态字段。
> **这就是实现拦截、修改、拒绝的载体。**

```
/// Harness内部，Hook/插件唯一可以操作的对象
struct SkillCallContext {
    // 来源信息
    pub call_id: String,
    pub tool_name: String,

    // ✅可变参数：hook可以修改！不是raw_arguments只读副本
    pub params: serde_json::Value,

    // Hook输出状态：核心！拦截能力全靠这几个状态位
    pub rejected: bool,
    pub reject_msg: Option<String>,
    pub warnings: Vec<String>,

    // 元信息：传给插件/契约，方便校验
    pub contract_tool_meta: Option<ToolMeta>,
}

impl SkillCallContext {
    /// 构造函数：把模型解析出来的只读Request → 可变Context
    pub fn from_request(req: SkillCallRequest) -> Self {
        Self {
            call_id: req.call_id,
            tool_name: req.tool_name,
            // 复制模型输出的原始参数到可变params，hook可以原地修改params
            params: req.raw_arguments,
            rejected: false,
            reject_msg: None,
            warnings: Vec::new(),
            contract_tool_meta: None,
        }
    }

    /// 给hook调用：标记拒绝，停止执行skill
    pub fn mark_reject(&mut self, msg: impl Into<String>) {
        self.rejected = true;
        self.reject_msg = Some(msg.into());
    }

    pub fn is_rejected(&self) -> bool {
        self.rejected
    }
}
```

> 
> 关键点：
> 
> 
> - `SkillCallRequest`：外部输入，来自LLM解析层，**不能改**。
> - `SkillCallContext`：Harness内部工作对象，**params可原地修改**。
> Hook可以：
> 
> 
> 1. 修改 `ctx.params["depart_time"]`（参数修正，时区归一化）
> 2. push warning
> 3. `mark_reject()` 直接否决本次skill调用，不真正调用MCP。

`from_request` 不是魔法，就是**复制原始数据，套一层可变状态壳子**。

## 业界流行Agent框架是不是这套？

### 1. OpenAI Codex‑CLI Harness ✅ 完全同思路

- LLM输出原始tool‑call JSON → 解析成内部`ToolCall` DTO；
- 包装为`ToolContext`可变对象，传入`PreToolUse` hook；
- hook可以修改参数、标记deny拒绝；拒绝后不执行系统命令/文件操作；> 
> Codex‑CLI的sandbox拒绝、参数改写，全部是在这个可变Context上完成。

### 2. Claude‑Code Harness ✅类似，但更保守

- 同样解析tool call为内部对象，传入pre‑exec钩子；
- **但是钩子不允许随意篡改参数**；只允许拒绝/告警；参数改写能力较弱。

### 3. Mastra / LangGraph / LlamaIndex Agent ❗**不一样，也是坑点来源**

绝大多数通用Agent框架：

> 
> LLM tool_call → 直接拿去执行tool；**hook拿到的大多是只读副本**。
> hook只能做日志，很难原地修改参数；拒绝能力弱，很多要抛异常来中断流程。

这就是为什么通用Agent框架做业务护栏很难：
它们的hook设计是**事件通知**（“即将调用工具，通知你一声”），不是**拦截器模式**（“交给你，你可以改、可以否决”）。

> 
> 区分两种Hook范式：

1. **事件通知Hook（LangGraph/Mastra默认）**：只是回调通知，无权阻止/改写；抛异常是粗暴中断手段。
2. **拦截器上下文Hook（Codex‑CLI / TravelKit Harness）**：传入可变上下文对象，**允许修改参数、显式标记拒绝，正常返回，不用抛异常**。

> 
> 这是关键差异：TravelKit Harness模仿Codex‑CLI，用**拦截器模式**，不是事件通知模式。
> 不要拿LangGraph的hook思维套过来。

### 4. MCP协议本身

MCP只是线上传输协议，只定义wire格式（`toolCall` JSON）。
MCP**本身没有hook、没有拦截、没有上下文对象**；拦截是上层Harness自己实现的。

# 完整跑一遍小例子，具象化

假设LLM输出原始tool call JSON字符串：

```

```

1. `llm_client.generate_skill_call`：解析文本，输出`SkillCallRequest`

```

    tool_name: "search_flight".to_string(),
    raw_arguments: json!({"depart_code":"BJ","arrive_code":"SHA","depart_time":"2026‑10‑01"}),
    call_id: "call‑001".to_string()
}
```

2. `SkillCallContext::from_request(req)`：复制数据，生成可变context

```
let mut ctx = SkillCallContext::from_request(req);
// ctx.params现在就是 {"depart_code":"BJ",...}，可写；rejected=false
```

3. 进入PreHook / 业务插件 IataCheckPlugin

}
```

4. Harness主循环检查 `ctx.is_rejected() → true`

- **不执行MCP search_flight**
- 把reject_msg写回会话历史，直接进入下一轮turn，让大模型重新生成tool_call。

> 
> 整个过程：**没有抛异常，没有panic；依靠上下文状态标记做控制流**。
> 这是Codex‑CLI非常重要的设计，业务校验失败属于正常业务流程，不是RuntimeError。

# 回答你最困惑的一句话：

> 
> “如何从skill文本描述到可以拦截的call intention”

1. LLM输出**文本/JSON**，由LLM Client层完成解析，产出只读DTO `SkillCallRequest`；
2. `SkillCallContext::from_request()` **不是做NLP意图解析**！它不做文本理解；只是把已经解析好的结构化tool‑call数据，包装成带可变状态的容器；
3. 真正的意图（这是search_flight），**是大模型输出+JSON解析得到的，不是Harness解析自然语言得到**。

> 
> ⚠️重要边界：
> Harness **不做自然语言意图识别**。
> Harness信任：LLM+解析层已经识别出tool_name；Harness只负责：校验这个调用的参数、允许/拒绝、修改参数。

如果LLM输出乱文本、不是合法tool‑call，在`llm_client.generate_skill_call`这一层就返回解析错误，直接进入`RuntimeError`终止，根本不会走到`from_request`。

# 和之前插件注册表架构结合

原来示例代码写的是 `Vec<Box<dyn PreSkillHook>>` 全局钩子链表（老写法）。
升级到插件注册表模式之后：
`PreSkillHook` 调度壳不再放业务逻辑；调度壳内部根据tool_name读取contract的`pre_plugin_ids`，从插件注册表取出业务插件，依次执行插件的`run_pre(&mut ctx)`。
**但是 SkillCallContext这套可变上下文对象完全不变，不需要改动。**

```
// 调度壳（属于框架，冻结）
struct ContractPreDispatchHook;
impl PreSkillHook for ContractPreDispatchHook {
    async fn before_call(&mut self, ctx: &mut SkillCallContext) {
        // 1. 从契约拿到当前tool要运行的业务插件id列表
        let meta = ctx.contract_tool_meta.as_ref().unwrap();
        // 2. 遍历插件注册表，执行业务插件
        for pid in &meta.pre_plugin_ids {
            let plugin = PLUGIN_REGISTRY.get_pre(pid).unwrap();
            plugin.run_pre(ctx).await;
            if ctx.is_rejected() {
                return; // 一旦被拒绝，直接停止后续插件
            }
        }
    }
}
```

> 
> 主循环只注册这一个全局PreSkillHook：`ContractPreDispatchHook`。
> 所有IATA、时间公理全部变成业务插件，不再写为独立全局hook塞入pre_skill_hooks vector。

## 执行时序（固定，不再变动）

```

        2. 预算counter全局检查，超限直接终止(BudgetExhausted)

```

pub trait PrePlugin: Send + Sync {
    async fn run_pre(&mut self, ctx: &mut SkillCallContext);
}

/// post时机业务插件统一trait
pub trait PostPlugin: Send + Sync {
    async fn run_post(&mut self, ctx: &mut SkillResultContext);
}

/// 插件注册表：框架容器，只管理注册查找，无业务
pub struct PluginRegistry {

    pub fn register(&mut self, id: String, plugin: Box<dyn PrePlugin + PostPlugin>);
    pub fn get_pre(&self, id: &str) -> Option<&Box<dyn PrePlugin>>;
    pub fn get_post(&self, id: &str) -> Option<&Box<dyn PostPlugin>>;
}

/// glob模式全局横切hook，框架层，仅用于日志/metrics/审计
pub struct PatternHookRegistry {
    // key: glob pattern字符串，value: 一批hook函数
}
```

Appendix III：hooks

你的这个方案是**带模式匹配的Hook注册表**，属于中间形态，介于「全局无脑跑全部hook」和「skill显式声明plugin_ids」两者之间。

>

```
// 注册表样例
hook_registry.register_pre("write_*", vec![func1, func2]);
hook_registry.register_pre("search_flight", vec![iata_check]);
hook_registry.register_pre("*", vec![audit_log]);
```

tool=`write_file` → 匹配`write_*` + 匹配兜底`*`，收集到func1、func2、audit_log依次执行。

# 模式匹配Hook Registry的细节坑（工程落地会踩）

### 1. 执行顺序是大麻烦

例子：

```
register_pre("*", [audit_log])
register_pre("search_*",[time_axiom])
register_pre("search_flight",[iata_check])
```

`search_flight`命中三条pattern，执行顺序：

- 方案1：按注册顺序；
- 方案2：pattern精确性优先（越具体越后执行）。

顺序错会直接导致bug：比如先做业务校验，再做审计日志；或者反过来。

> 
> 显式plugin_ids没有这个问题：列表顺序就是执行顺序。

### 2. 隐式依赖，调试成本上升

问题：我现在看`search_flight`的contract JSON，**看不到它会被哪些hook处理**。
必须去遍历整个hook注册表所有pattern，模拟匹配，才能得到实际执行函数集合。

- 单元测试、golden case、文档生成都要额外写一套“模拟匹配推演”工具；
- 线上出bug，第一反应：这个tool到底跑了哪些hook？不能直接看契约。

> 
> Codex‑CLI没有大规模用glob模式，一部分原因就是可观测性。

###3. 不能方便“排除”
假设：绝大多数tool都需要`audit_log`，唯独某一个内部调试tool不需要。

- 模式匹配方案：`*`会全部命中；没有“排除pattern”的原生能力；要写复杂负向glob，很别扭。
- 显式plugin_ids：该tool不写audit插件id即可。

###4. Tool改名的静默故障
`search_flight`改名叫`search_roundtrip_flight`，原来pattern`search_flight`不再匹配，校验全部消失，**没有编译报错，运行时静默失效**。
显式plugin_ids：tool名字和插件id解耦；tool改名不影响插件引用。

# 最佳融合方案（可以两者结合，吸收两边优点）

> 
> 现实工程可以：**两层机制共存**

1. **第一层：全局模式匹配Hook Registry**
用于：横切关注点：审计日志、metrics统计、token计数、权限基础拦截。
用glob pattern，`*`、`search_*`这类，**只放无业务副作用的横切逻辑**。
2. **第二层：每个tool在contract显式声明 pre_plugin_ids / post_plugin_ids**
用于：**业务领域校验（IATA、时间公理、舱位规则）**，精确、显式、可观测。

执行顺序：
`全局模式匹配hook(先执行) → 本tool契约声明的插件集合(后执行)`

伪代码片段：

```
// 1.全局模式注册表，只放横切：日志、埋点、基础权限
let global_hooks = PatternHookRegistry::new();
global_hooks.register_pre("*", vec![audit_log, metrics_collect]);

// 2.每个tool契约声明业务插件
let tool_meta = ctx.contract.get_tool_meta(&ctx.tool_name);

// 执行流程
// step1：glob匹配，跑全局横切hook
let global_matched = global_hooks.match_pre(ctx.tool_name);
for hook in global_matched { hook(ctx).await; }

// step2：执行该tool显式声明的业务插件
for pid in &tool_meta.pre_plugin_ids {
    let plugin = plugin_registry.get(pid).unwrap();
    plugin.run_pre(ctx).await;
}
```

###取舍边界

- ✅横切（日志、埋点、基础统计）交给glob模式hook registry，不用每个tool重复写。
- ✅业务公理、IATA、时间校验这类业务约束，**坚决不走glob模式，走contract显式plugin_ids**，保证可见、可静态检查、无隐式匹配陷阱。

###关于DSL的兼容
你说hook可以是原生函数，也可以是DSL预编译出来的闭包：

> 
> 允许，但遵循隔离原则：
> 全局模式hook和业务插件都可以挂载预编译DSL闭包；**但不要把复杂业务公理写在DSL表达式里**；简单转换可以，复杂逻辑优先手写插件，避开maxlang解析/闭包坑。

# 总结

1. 模式匹配Hook Registry本身技术可行，**非常适合横切类通用逻辑**；不要把业务校验全部塞进去。
2. 如果把业务公理也全部交给glob正则匹配，会得到一套隐式系统：调试、排错、静态校验代价很高。
3. 推荐两层组合：glob‑hook registry处理横切；contract显式plugin_ids处理业务校验；两者并存，各司其职。

> 
> 类比后端开发：
> glob‑hook registry ≈ web框架中间件（日志、cors，全部路由生效）
> contract plugin_ids ≈ 每个接口controller显式声明自己的业务校验器。

# 四人格分析
**正向完善**
你的理解高度击中Harness工程化本质：Harness不是通用Agent框架，是**面向特定工作流的执行外壳**。
- 小模型Harness补脑：小模型推理弱，靠Harness内置fence、counter、状态机、校验规则，补全逻辑、边界、重试、约束，拖拽模型按流程走完任务；

Harness作用域：单项目 > 一类项目，不追求跨领域通用；通用Agent是模型自带能力，Harness是外部“工程护栏”。

**反向挑错**
1. 不是绝对“一个项目一套”，同类项目可以复用一套Harness，只替换配置/Goal，不需要重写全部代码；
2. “拖着不太聪明的模型”有局限：Harness不能凭空创造能力，只能约束和校验，如果模型完全看不懂子任务，再多护栏也会持续失败；
3. 大模型Harness不只守底线，也会做流程切片、任务拆分，不只是拦截错误输出。

**查证人格**
业界Harness(Agent‑Harness)定位：测试/执行脚手架，负责状态流转、输入输出校验、失败重试、断言、规则拦截；**和模型解耦，但绑定业务工作流**。
- 通用Agent：模型内部做规划、反思；
- Harness范式：外部系统做规划、状态、校验，模型只做单步生成。
你的“小模型补脑，大模型守底线”是工程落地非常典型的实践模式。

**总结判断**
> 核心结论：✅大体正确。
Harness绑定**特定业务流程/项目类型**，不属于通用Agent；
- 小模型：Harness充当外部大脑，补流程、边界、纠错，驱动模型干活；
- 大模型：Harness主要充当护栏，守住这套特定工作流的规则、断言、合规底线；
可以一类项目共用一套Harness，靠配置隔离，不必每个项目完全重写；Harness无法弥补模型本身基础能力缺失。

一句话浓缩：**Agent是模型想怎么做；Harness是规定这件事必须怎么做。**

# Codex‑CLI Harness完整分析
> 定位：**面向软件开发场景的专用Agent运行时Harness**，不是通用Agent框架；模型只负责生成工具调用，**全部执行、安全、循环、上下文、预算、权限由Harness接管**。
> 核心理念：`Agent = Model + Harness`；模型不直接碰OS/文件系统，所有外部交互必须经过Harness护栏。

## 一、核心功能
1. **Agent主循环驱动**：朴素turn‑base循环，驱动模型→工具调用→结果回灌模型，4种终止条件：任务完成、预算耗尽、用户终止、错误中止。
2. **系统级沙箱安全围栏(fence)**：内核级隔离，限制读写范围、命令执行、网络访问，Workspace外文件默认不可修改；区分只读/修改/高危操作，审批策略可配置。
3. **预算计数器(counter)**：全局累计轮次、token、工具调用次数，防止无限Agent循环（IAL无限循环防护），不是单函数局部max_retry，是进程级全局记账。
4. **上下文工程(compaction)**：自动压缩超长会话；不是简单摘要，会**重编排历史、重注入项目初始上下文**，支持会话中断后resume续跑。
5. **钩子中间件Hooks**：`PreToolUse`/`PostToolUse`；工具执行前后拦截、改写参数、注入校验、自动跑单元测试、拒绝高危模式，实现项目专属规则。
6. **工具注册表+MCP对接**：文件读写、diff、bash、git；原生MCP客户端，可扩展自定义skill；工具调用全部经过权限校验层，模型不能直接调用系统API。
7. **会话状态持久化**：SQLite保存审批记录、轮次、世界状态、日志，重启恢复会话；完整session日志输出用于离线评测、故障复现。
8. **多运行入口**：交互式TUI、批处理`codex exec`、IDE App‑Server；同一套harness内核，不同前端接入。

## 二、主要模块（Rust workspace crate划分）
| 模块 | 职责 |
|---|---|
| **core** | Agent主循环、turn调度、工具分发、compaction压缩、全局预算counter；Harness心脏 |
| **protocol** | 协议结构体：工具定义、审批请求、SandboxPolicy、TurnAbortReason；跨组件统一契约 |
| **sandboxing(linux‑sandbox/windows‑sandbox‑rs)** | 系统级沙箱：Linux Landlock，macOS Seatbelt，Windows WSL2受限token；**fence安全护栏实现层** |
| **tools** | 内置工具实现(read/write/edit/bash/git)；参数校验；钩子注入点 |
| **services** | 会话DB、日志持久化、状态存储；保存counter计数、用户审批决策 |
| **hooks** | PreToolUse / PostToolUse中间件；加载项目`requirements.toml`配置钩子，企业侧管理员强制规则，开发者不可覆盖 |

## 三、设计逻辑（非常贴合你前面“小模型补脑，大模型守底线”）
1. **场景绑定，不做通用**：专门面向软件工程项目；一套harness可以服务一类代码项目，靠`AGENTS.md`+`requirements.toml`注入项目特有规则，不用改harness内核代码。
    - **小模型模式（补脑）**：harness提供强循环、沙箱、重试、钩子校验；弥补小模型规划差，拖拽模型一步一步完成编码任务。模型只管输出工具调用，规划、边界、失败恢复交给harness。
    - **大模型模式（守底线）**：模型擅长规划推理；harness主要做安全围栏、全局预算、禁止越权操作、执行后校验，防止幻觉删文件、死循环、越出workspace。
2. **不信任模型原则**：**不相信模型输出的任何工具参数**；全部工具入参过hooks、sandbox策略、权限校验。模型生成只是“申请”，harness决定是否放行执行。
3. **薄内核，配置驱动规则**：harness内核只实现循环、沙箱、预算、钩子机制；业务规则（“必须跑单元测试”“禁止rm‑rf”）不写死内核，放在钩子、AGENTS.md、requirements.toml。同类项目复用harness内核，替换配置即可。
4. **全局counter，对抗无限循环**：不是每个工具单独设置重试次数；全局统计turn数、工具调用总量，从最外层切断Agent死循环路径。
5. **世界状态外部维护**：文件变更、审批记录保存在harness侧，不完全依赖模型记忆；会话恢复时重新注入真实环境状态，不依赖摘要里的过时信息。

> 和LangGraph/CrewAI关键区别：LangGraph是编排SDK，循环、状态、安全、持久化全部需要自己写；Codex‑CLI Harness是**完整运行时**，安全、循环、压缩、沙箱全部内置，开发者填业务规则即可。

## 四、实现逻辑：一轮Turn完整流程
```
1. Harness读取：config.toml + requirements.toml + AGENTS.md + 当前会话状态DB
2. Compaction上下文管理器：组装prompt，必要时压缩旧历史，重注入项目基础上下文
3. 调用LLM，拿到模型输出的工具调用申请
4. PreToolUse钩子链执行：
   ├─改写工具参数
   ├─fence安全策略校验（沙箱规则、白名单）
   └─counter全局预算检查（轮次/调用数是否超限）
5. 判断是否需要用户人工审批；需要则暂停，保存审批状态到DB
6. 沙箱内执行工具；严格限制syscall、文件访问、网络
7. PostToolUse钩子链执行：
   ├─自动跑编译/单元测试
   └─注入额外提示给模型，把失败结果回传给模型
8. 工具执行结果回写会话历史、更新世界状态、更新counter计数
9. 判断TurnAbortReason：完成/超限/用户终止/报错；不满足退出条件，回到步骤2继续循环
```
4种终止原因：
- TaskComplete：Harness识别任务结束
- BudgetExhausted：全局counter耗尽
- UserAbort：用户中断
- RuntimeError：执行异常

## 五、对应到你自研Travelkit订票Harness的启发
1. 不要把订票业务公理写死循环内核；把公理、IATA校验、时区规则放到类似`PreToolUse/PostToolUse`钩子层；harness内核只维护循环、状态、计数器、会话持久化。

    query_api_counter: u32,         // 航班接口调用计数
    max_api_query: u32,

    // -------- 会话状态存储(外部LibSQL，世界状态不由模型记忆) --------
    session_store: SessionStore,

    // -------- 钩子链：对应 Codex‑CLI PreToolUse / PostToolUse --------
    pre_skill_hooks: Vec<Box<dyn PreSkillHook>>,
    post_skill_hooks: Vec<Box<dyn PostSkillHook>>,

    // -------- LLM模型句柄；Harness不关心具体模型实现 --------
    llm_client: Box<dyn LlmProvider>,

    // -------- Skill契约定义 travel‑skill‑contract‑v2.json --------
    skill_contract: SkillContract,
}

/// 一次轮次的返回结果；定义所有终止原因，对齐Codex‑CLI TurnAbortReason
#[derive(Debug)]
enum HarnessExitReason {
    TaskComplete,          // 拿到满足约束的航班方案，正常结束
    BudgetExhausted,       // counter耗尽，强制终止
    UserAbort,             // 用户主动停止
    BusinessRuleReject,    // 业务公理校验持续失败，终止
    RuntimeError,
}

impl TravelKitHarness {
    /// 主入口：启动Harness执行会话，对应 codex exec
    pub async fn run(&mut self, user_query: &str) -> HarnessExitReason {
        // 初始化会话，加载历史状态、契约配置
        self.session_store.init(user_query);
        self.reset_counters();

        loop {
            // 【1】全局预算检查：外层拦截死循环，Codex‑CLI核心思想
            if self.global_turn_counter >= self.max_global_turn {
                return HarnessExitReason::BudgetExhausted;
            }

            // 组装prompt：读取会话历史 + skill契约；必要时做上下文压缩
            let prompt_ctx = self.session_store.build_llm_context().await;

            // 【2】调用大模型：模型输出Skill调用申请，仅仅是“申请”
            let skill_call_request = self.llm_client.generate_skill_call(prompt_ctx).await;

            // ===== PreSkillHook 链（等价 Codex‑CLI PreToolUse）=====
            // 在这里执行：IATA码校验、时区转换、航旅公理校验、参数补全/拒绝
            // ✨ 所有订票业务规则写在这里，**不污染Harness主循环内核**
            let mut call_ctx = SkillCallContext::from_request(skill_call_request);
            for hook in &mut self.pre_skill_hooks {
                // hook可以：修正参数、打警告标记、直接拒绝本次调用
                hook.before_call(&mut call_ctx).await;
                if call_ctx.is_rejected() {
                    // 业务规则拒绝，把拒绝原因写回会话，进入下一轮
                    self.session_store.append_reject_log(&call_ctx.reject_msg).await;
                    self.global_turn_counter += 1;
                    continue;
                }
            }

            // 【3】真正执行Skill（航班查询等）
            let skill_result = self.skill_contract.execute_skill(&call_ctx).await;
            self.query_api_counter += 1;

            // ===== PostSkillHook链（等价 Codex‑CLI PostToolUse）=====
            // 校验返回航班结果是否符合公理；注入错误提示给模型
            let mut result_ctx = SkillResultContext::new(&call_ctx, skill_result);
            for hook in &mut self.post_skill_hooks {
                hook.after_call(&mut result_ctx).await;
            }

            // 【4】更新外部世界状态：存入LibSQL，不依赖模型记忆
            self.session_store.append_skill_result(&result_ctx).await;
            self.global_turn_counter += 1;

            // 【5】终止判断：是否已经拿到满足用户约束的航班方案
            if self.check_task_complete(&result_ctx) {
                return HarnessExitReason::TaskComplete;
            }

            // 额外防护：查询接口超限提前终止
            if self.query_api_counter >= self.max_api_query {
                return HarnessExitReason::BudgetExhausted;
            }
        }
    }

    /// 判断任务是否完成：Harness侧断言，不是模型自己说“我做完了”
    fn check_task_complete(&self, res_ctx: &SkillResultContext) -> bool {
        // Harness做客观断言：有有效航班、全部用户约束被满足
        // 不采信模型输出的"任务完成"字符串，和Codex‑CLI思想一致
        res_ctx.has_valid_flights() && res_ctx.all_user_constraint_satisfied()
    }

    fn reset_counters(&mut self) {
        self.global_turn_counter = 0;
        self.query_api_counter = 0;
    }
}

/// Hook Trait定义：业务规则全部实现这个trait，可插拔
trait PreSkillHook {
    async fn before_call(&mut self, ctx: &mut SkillCallContext);
}
trait PostSkillHook {
    async fn after_call(&mut self, ctx: &mut SkillResultContext);
}

// ---------------- 示例业务Hook实现（订票业务，不属于Harness内核） ----------------
/// Hook示例：IATA城市/机场码校验，属于业务钩子，不侵入Harness循环内核
struct IataCodeValidateHook;
impl PreSkillHook for IataCodeValidateHook {
    async fn before_call(&mut self, ctx: &mut SkillCallContext) {
        if !is_valid_iata_code(ctx.params.depart_code) {
            ctx.mark_reject("出发地IATA码非法，请修正城市/机场代码");
        }
    }
}

/// Hook示例：时区、时间公理校验
struct TimeAxiomCheckHook;
impl PreSkillHook for TimeAxiomCheckHook {
    async fn before_call(&mut self, ctx: &mut SkillCallContext) {
        // 做时区归一化、时间边界校验，修正模型传错的时间参数
        ctx.normalize_timezone_params();
        if violates_flight_time_axiom(&ctx.params) {
            ctx.mark_reject("时间参数违反航旅公理，需要重新生成查询条件");
        }
    }
}

## 关键设计点对照Codex‑CLI

1. Harness内核代码**完全没有一行订票业务代码**；所有IATA、时区、公理全部是可插拔Hook，对应Codex‑CLI把业务规则放到`requirements.toml`钩子。
2. 全局counter在外层loop，不是工具内部重试，从根源避免Agent无限轮次疯狂调用航班接口。
3. **不相信模型的自判断**：`check_task_complete()`是Harness客观断言，不是看模型说“任务完成”。
4. 会话世界状态保存在外部存储(LibSQL)，不完全依赖模型上下文记忆约束。
5. Skill调用是“申请‑校验‑放行”流程，复刻Codex‑CLI：模型只生成申请，Harness拥有否决权。
